# Бриф: форк widgetsack под личный Windows-дашборд

> Файл для Claude Code. Положить в корень форка рядом с `AGENTS.md`.
> Claude Code: прочитай этот файл целиком, затем `AGENTS.md`, затем `docs/dev/*.md`, и только после этого предлагай план.

## 1. Что делаем

Форкаем [gyng/widgetsack](https://github.com/gyng/widgetsack) (Tauri 2 + React/TypeScript + Rust, лицензия MIT/Apache-2.0) и добавляем **встроенные** виджеты под мои задачи. Целевая платформа — только Windows 10/11.

Три фичи, по приоритету:

1. **Server check** — доступность моих удалённых серверов (несколько VPS + локальные хосты в сети).
2. **Camera** — живой просмотр RTSP-потоков с IP-камер в локальной сети.
3. **Calendar / agenda** — ближайшие события из моего календаря (ICS-фид или CalDAV).

Плюс сквозное: всё должно переживать перезагрузку (автозапуск), конфиг — в одном понятном месте, секреты (пароли камер, токены) — не в git.

## 2. Ключевое архитектурное ограничение

В widgetsack есть система внешних плагин-пакетов (`plugin.json` + JS-сенсор). **Она нам не подходит**: песочница JS-сенсора не имеет доступа к сети/Tauri/FS, хост делает за неё только HTTPS GET к одобренным публичным хостам, IP-литералы, порты и локальные имена отклоняются.

Поэтому все три фичи реализуем как **встроенные типы виджетов**: React-компонент во фронте + Rust-команда/сенсор в `src-tauri`. Rust-сторона ничем не ограничена.

## 3. Правила работы (для Claude Code)

- **Сначала карта, потом код.** Первая задача — разобраться и письменно описать: где регистрируются типы виджетов, как устроен telemetry hub и сенсоры, как фронт получает данные из Rust (команды / события / polling), где живёт конфиг и как он валидируется, как устроены пресеты/шаблоны. Сохранить это в `docs/dev/fork-architecture-notes.md`.
- **Минимальное вторжение в ядро.** Новый код — в отдельных модулях/папках (например `src/widgets/fork/*`, `src-tauri/src/fork/*`), в ядро — только точки регистрации. Цель: уметь мержить апстрим без боли.
- **Переиспользуй существующее.** В репо уже есть ping-виджет (пресет Gaming), calendar/agenda-виджеты и Home Assistant health card. Перед тем как писать своё — проверь, что из этого можно расширить, а не дублировать.
- **Не ломай существующие виджеты.** После каждого этапа — прогон проверок из `docs/dev/development.md` (lint, typecheck, cargo check/test, сборка).
- **Коммит на каждый логический шаг**, осмысленные сообщения. Ветка на каждый этап: `feat/server-check`, `feat/camera`, `feat/calendar`.
- **Спрашивай, если выбор неочевиден** (формат конфига, где хранить секреты, какой транспорт для видео). Не делай больших рефакторингов молча.
- **Секреты не в репо.** Пароли камер, URL с кредами, токены — в отдельный файл в `%APPDATA%` или через Windows Credential Manager; в git — только пример-шаблон.
- Код и комментарии — на английском, объяснения мне — на русском.

### Этап 1 — Server check widget

Функционал:
- Список целей в конфиге: имя, хост (IP или DNS), тип проверки — `icmp` (ping), `tcp` (хост:порт), `http(s)` (URL, ожидаемый код/ключевое слово). Опционально: `ssh` (просто TCP на 22 + баннер, без аутентификации).
- Интервал опроса настраиваемый (дефолт 30 с), таймаут настраиваемый.
- Для каждой цели: статус up/down/degraded, последняя latency, мини-спарклайн latency за N последних проверок, время последнего падения.
- Визуально — в стиле существующих карточек widgetsack (использовать design tokens из `docs/dev/design-system.md`), цвет статуса через токены темы, не хардкод.
- Опционально: Windows-уведомление при переходе up→down (если в Tauri уже подключён notification plugin — использовать его).

Реализация:
- Rust: отдельный модуль-сенсор, публикует значения в telemetry hub по тому же паттерну, что и системные метрики. ICMP на Windows может требовать прав — если так, fallback на TCP и явно сказать об этом в UI.
- Front: новый тип виджета, зарегистрированный там же, где остальные.
- Конфиг целей — в основном конфиге приложения (или рядом, если так принято в репо), с валидацией и понятной ошибкой при опечатке.

Готово, когда: добавил 3 цели в конфиг → вижу их статус и latency на оверлее, падение одной из них отражается в течение одного интервала.

### Этап 2 — Camera widget (RTSP через go2rtc)

Подход: видео не декодируем сами. Рядом запускается [go2rtc](https://github.com/AlexxIT/go2rtc) (один бинарник, Windows), он берёт RTSP с камер и отдаёт WebRTC / MSE в браузер. Виджет — это `<video>`-плеер, подключающийся к go2rtc.

Функционал:
- Конфиг: адрес go2rtc API (дефолт `http://127.0.0.1:1984`), список стримов (имя в go2rtc → подпись на виджете).
- Виджет показывает один стрим, размер настраиваемый; отдельно — вариант «сетка» 2×2 из нескольких виджетов (или один виджет с несколькими стримами — выбрать по архитектуре раскладок).
- Транспорт: сначала WebRTC, при неудаче — MSE. Индикатор «нет сигнала»/реконнект.
- Оверлей по умолчанию click-through: нужен режим, в котором клик по виджету открывает стрим крупно (или просто не делаем интерактив — согласовать).
- Пауза воспроизведения, когда оверлей скрыт/свёрнут — не жечь CPU впустую.

Реализация:
- Front: компонент плеера. Можно опереться на `video-rtc.js` из репо go2rtc (там готовый веб-компонент для WebRTC/MSE) — проверить лицензию и способ подключения.
- Rust: опционально — команда «проверить, что go2rtc жив» и, если согласуем, автозапуск бинарника go2rtc как дочернего процесса (путь к бинарнику в конфиге).
- Проверить, что WebView2 на Windows даёт автоплей muted-видео и WebRTC к localhost без лишних флагов; если нужны настройки webview — задокументировать.
- Отдельно: сгенерировать пример `go2rtc.yaml` с одним RTSP-стримом (кредов в репо не класть).

Готово, когда: go2rtc запущен с одной камерой → на оверлее живое видео с задержкой до ~1 с, при отключении камеры виджет показывает «нет сигнала» и сам переподключается.

### Этап 3 — Calendar / agenda

Сначала **аудит существующего**: в репо есть calendar и agenda виджеты, фиды настраиваются в Plugins. Выяснить: какой формат фида поддержан (ICS? только HTTPS? ограничения песочницы?), можно ли подключить мой календарь как есть.

Если существующего достаточно — этап сводится к настройке и, возможно, мелким доработкам отображения.

Если нет — встроенный сенсор:
- Rust: загрузка ICS по URL (включая приватные ссылки Google/Яндекс/Outlook) или CalDAV (basic auth), парсинг (готовый crate), разворачивание RRULE на ближайшие N дней, кэш на диске.
- Front: agenda «сегодня / завтра / неделя», подсветка ближайшего события, обратный отсчёт до него.
- Секреты (URL с токеном, пароль CalDAV) — не в основном конфиге, см. правило про секреты.

Готово, когда: события из моего календаря видны на оверлее, обновляются без перезапуска.

- [ ] Автозапуск при входе в систему (Tauri autostart plugin или ярлык в Startup — что уже используется в репо).
- [ ] Один файл-пример конфига `config.example.*` со всеми тремя виджетами и комментариями.

## 6. Чего НЕ делать

- Не переписывать ядро widgetsack, не менять формат существующих раскладок.
- Не тащить тяжёлые зависимости для видео (ffmpeg-библиотеки, GStreamer) — декодирование делает go2rtc + браузер.
- Не класть IP, пароли и токены в репозиторий, даже в тестах.
- Не трогать кроссплатформенность ради Windows-only фич там, где это бесплатно сохранить; но и не тратить время на macOS/Linux.
